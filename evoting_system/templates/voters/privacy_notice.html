What is collected, and why

  • National ID number. Stored only as a SHA-256 hash; the number itself is not stored. Used to recognise you when you log in and to make sure the same person cannot register twice.
  • Full name. Stored as you type it at registration. Part of your voter record.
  • Phone number. Stored as you type it at registration. Used to send you a one-time passcode when you log in.
  • Registration time. The date and time you registered is stored with your voter record.
  • One-time passcode (OTP). A new 6-digit code is generated each time you log in and is valid for 5 minutes. Only a SHA-256 hash of it is stored, and that hash is cleared once you enter the code correctly. In this prototype no real SMS is sent: the code and your phone number are written to the server's application log, and when the server runs in debug mode the code is also shown on screen. Used to confirm that you control the registered phone.
  • Voting session token. After you pass the OTP step, a single-use token is created for about 15 minutes and is tied to your voter record. It is deactivated when you cast your ballot. Used so that only an authenticated voter can submit one ballot.
  • Participation record. For each election you vote in, the system records that you voted in that election and when. It records nothing about which candidate you chose. Used to enforce one vote per election.
  • Audit-log entry. When a ballot is cast, the system adds an entry containing the time, an action label, a SHA-256 hash of the ballot and the hash of the previous entry. It contains no name, phone number or ID. Used so that the record of votes can be checked for tampering.

Your ballot is not linked to you

  • A stored ballot contains only the election, the candidate chosen and the time it was recorded. The database has no field connecting a ballot to a voter or to a session token. This is built into the data structure, not a setting.
  • Recording the ballot, writing the audit-log entry, deactivating your token and marking that you voted all happen in one database transaction: either all of them are saved or none are.
  • The participation record has no link to a ballot or a candidate, and no ballot or candidate points back to it.
  • The audit log is designed to accept new entries only. The project's setup guide describes a restricted database role that is not allowed to change or delete audit-log rows, so that the limit is enforced by PostgreSQL itself and not only by the application.

Who can see what

  • Anyone (no login). For an election whose results have been published: the vote count for each candidate, the verification proof and the audit-log hashes. Nothing that identifies a voter.
  • Officials. Election status, turnout and candidate lists, and the results of published elections. Not individual voters and not individual ballots.
  • Auditors. The audit-log entries (time, action label and hashes) and the tool that checks the log's hash chain. Not voter names, phone numbers or ballots.
  • Administrators. The administration site is used to manage elections and candidates. It does not list voter records or session tokens.

These limits describe what the application's own pages show. Someone with direct access to the database server is not limited by them.
